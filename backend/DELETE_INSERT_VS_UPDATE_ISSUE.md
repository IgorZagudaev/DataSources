# Проблема DELETE/INSERT вместо UPDATE

## Описание проблемы

При изменении любого поля (например, названия доклада) в логах SQL наблюдаются операции DELETE всех таблиц и INSERT всех данных, вместо простой операции UPDATE одной записи.

## Причина

Это фундаментальная архитектурная проблема текущей реализации синхронизации.

### Как работает сейчас:

```
1. Пользователь изменяет поле (например, название доклада)
   ↓
2. Фронтенд обновляет данные в localStorage
   ↓
3. Вызывается функция notify()
   ↓
4. notify() вызывает syncToAPI()
   ↓
5. syncToAPI() отправляет ВСЕ данные через POST /api/import
   ↓
6. handleImport() выполняет:
   - DELETE FROM data_sources
   - DELETE FROM data_slices
   - DELETE FROM indicators
   - DELETE FROM note_blocks
   - DELETE FROM notes
   - DELETE FROM sections
   - DELETE FROM reports
   ↓
7. Затем INSERT всех данных заново
```

### Почему так сделано:

1. **Историческая причина** - приложение изначально работало только с localStorage
2. **Простота реализации** - не нужно было создавать отдельные endpoint'ы для каждой операции
3. **Синхронизация состояния** - гарантируется, что БД и фронтенд всегда синхронизированы
4. **Поддержка импорта** - тот же механизм используется для импорта данных

## Последствия

### Негативные:

1. **Производительность**
   - При изменении одного поля перезаписываются ВСЕ данные
   - Нагрузка на БД пропорциональна объёму данных, а не объёму изменений
   - Медленная работа при большом количестве данных

2. **Риск потери данных**
   - При race condition (одновременные изменения) возможна потеря данных
   - Если DELETE выполнен, но INSERT не завершён - данные потеряны
   - Нет транзакционной безопасности

3. **Блокировки таблиц**
   - DELETE блокирует таблицы
   - Другие пользователи не могут читать данные во время синхронизации
   - Возможны deadlock'и

4. **Нагрузка на сеть**
   - Передаются ВСЕ данные при каждом изменении
   - Большой объём трафика
   - Медленная работа при плохом соединении

### Позитивные:

1. **Простота** - не нужно отслеживать, что именно изменилось
2. **Надёжность** - БД всегда содержит полную копию данных
3. **Совместимость** - работает с существующим кодом без изменений

## Решение

### Вариант 1: Оптимизация текущей архитектуры (краткосрочное)

**Идея:** Добавить отслеживание изменений и отправлять только изменённые данные.

**Преимущества:**
- Относительно простая реализация
- Сохраняет совместимость с существующим кодом
- Уменьшает нагрузку на БД

**Недостатки:**
- Всё ещё требует DELETE/INSERT для изменённых записей
- Сложная логика отслеживания изменений
- Риск рассинхронизации состояния

**Реализация:**
```typescript
// Отслеживание изменений
const changes: Change[] = [];

function trackChange(type: string, action: string, data: any) {
  changes.push({ type, action, data, timestamp: Date.now() });
}

// Отправка только изменений
async function syncChanges() {
  if (changes.length === 0) return;
  
  await api.applyChanges(changes);
  changes = [];
}
```

### Вариант 2: Переход на REST API (долгосрочное, рекомендуется)

**Идея:** Использовать отдельные endpoint'ы для каждой CRUD операции.

**Преимущества:**
- ✅ Максимальная производительность
- ✅ Только необходимые операции (UPDATE вместо DELETE/INSERT)
- ✅ Транзакционная безопасность
- ✅ Меньше нагрузка на сеть
- ✅ Стандартная архитектура REST API

**Недостатки:**
- ❌ Требует значительной переработки фронтенда
- ❌ Нужно отслеживать состояние каждой сущности
- ❌ Сложнее реализация

**Реализация:**

#### 1. Фронтенд (src/store.ts)

Заменить синхронизацию всех данных на прямые вызовы API:

```typescript
// Было:
export function updateReport(id: string, name: string, description?: string) {
  reports = reports.map(r => r.id === id ? { ...r, name, description } : r);
  notify(); // ← Вызывает syncToAPI() → DELETE/INSERT всех данных
}

// Стало:
export async function updateReport(id: string, name: string, description?: string) {
  // Обновляем локальное состояние
  reports = reports.map(r => r.id === id ? { ...r, name, description } : r);
  
  // Отправляем только изменение
  try {
    await api.updateReport(id, { name, description });
  } catch (error) {
    // Откатываем изменения при ошибке
    console.error('Failed to update report:', error);
    // ... логика отката
  }
}
```

#### 2. API endpoints (уже существуют)

```php
// PUT /api/reports/{id}
case 'PUT':
    $sql = "UPDATE reports SET name = ?, description = ? WHERE id = ?";
    $params = [$input['name'], $input['description'] ?? null, $id];
    $stmt = $db->prepare($sql);
    $stmt->execute($params);
    logAction('edit', 'report', $id, $input['name']);
    echo json_encode(['success' => true]);
    break;
```

#### 3. Преимущества

**Было:**
```
Изменение названия доклада → Отправка всех данных → DELETE всех таблиц → INSERT всех данных
Время: 2-5 секунд
Нагрузка: высокая
```

**Стало:**
```
Изменение названия доклада → Отправка одного запроса → UPDATE одной записи
Время: 50-200 мс
Нагрузка: минимальная
```

### Вариант 3: Гибридный подход (компромиссное)

**Идея:** Использовать REST API для CRUD операций, но сохранить синхронизацию для импорта/экспорта.

**Преимущества:**
- Баланс между производительностью и сложностью
- Постепенная миграция
- Сохранение обратной совместимости

**Реализация:**

1. **CRUD операции** → прямые вызовы API
2. **Импорт/экспорт** → синхронизация всех данных
3. **Синхронизация при старте** → загрузка всех данных

## Рекомендации

### Для продакшена (срочно):

1. **Вариант 1** - оптимизация текущей архитектуры
   - Быстрая реализация
   - Уменьшает нагрузку в 5-10 раз
   - Минимальные изменения в коде

### Для развития (долгосрочно):

2. **Вариант 2** - переход на REST API
   - Максимальная производительность
   - Стандартная архитектура
   - Требует переработки фронтенда

### Для тестирования:

   - Постепенная миграция
   - Можно тестировать отдельные компоненты

## Временное решение

Пока не реализована оптимизация, можно:

1. **Отключить автоматическую синхронизацию**
   ```typescript
   function notify() {
     saveData(reports);
     listeners.forEach(l => l());
     // Временно отключено
     // if (currentMode === 'api' && !isLoadingFromAPI) {
     //   syncToAPI();
     // }
   }
   ```

2. **Синхронизировать вручную**
   - Добавить кнопку "Синхронизировать с сервером"
   - Синхронизировать только при сохранении

3. **Использовать debounce**
   ```typescript
   let syncTimeout: NodeJS.Timeout;
   
   function notify() {
     saveData(reports);
     listeners.forEach(l => l());
     
     if (currentMode === 'api' && !isLoadingFromAPI) {
       clearTimeout(syncTimeout);
       syncTimeout = setTimeout(() => {
         syncToAPI();
       }, 5000); // Синхронизация через 5 секунд после последнего изменения
     }
   }
   ```

## Мониторинг

### Проверка нагрузки

```sql
-- Количество операций DELETE/INSERT за последний час
SELECT 
  DATE_TRUNC('hour', created_at) as hour,
  COUNT(*) as operations
FROM (
  SELECT created_at FROM reports
  UNION ALL
  SELECT created_at FROM sections
  UNION ALL
  SELECT created_at FROM notes
) as all_operations
WHERE created_at > NOW() - INTERVAL '1 hour'
GROUP BY DATE_TRUNC('hour', created_at)
ORDER BY hour;
```

### Проверка времени выполнения

```sql
-- Среднее время выполнения операций
SELECT 
  schemaname,
  relname,
  seq_scan,
  seq_tup_read,
  idx_scan,
  idx_tup_fetch
FROM pg_stat_user_tables
ORDER BY seq_tup_read DESC;
```

**Рекомендуемый порядок действий:**

3. **Долгосрочно** - перейти на Вариант 2 (REST API)

Это значительно улучшит производительность и надёжность системы.
